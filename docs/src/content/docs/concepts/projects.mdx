SDD works on **projects**: units with their own stack and commands. `/sdd:doctor init` finds them (an Nx or Turborepo workspace, pnpm/yarn/uv/Cargo/Go workspaces, Gradle includes, stray manifests like `apps/api/pyproject.toml`) and asks which sibling repositories belong to the product.

<CardGrid>
  <Card title="Single app" icon="laptop">
    One project, `root`. The simplest setup.
  </Card>
  <Card title="Monorepo" icon="seti:folder">
    One project per app or package, each with its own commands and implementer.
  </Card>
  <Card title="Several repositories" icon="random">

## What a project gives you

| Where | What |
|---|---|
| `capabilities.yml` → `projects` | Name, kind (web, backend, mobile, library, e2e …), path and stack. |
| `implementation.projects.<name>` | A different implementer per project. |
| Constitution §2 | One command row per project: `test`, `coverage`, `typecheck`, `lint`, `dev`. |

A Python API runs `cd apps/api && uv run pytest`, the web app `pnpm nx run web:test`, a Flutter app `flutter test`.

<Aside type="tip" title="No fixed list of stacks">
`init` reads declared scripts, CI and pre-commit config and tool config files, for any language or tool. Supporting a new tool usually requires editing nothing.
</Aside>

## Several repositories

- Everyone checks the sibling repos out **next to the spec repo** under the same names (the relative paths are committed).
- `/sdd:implement` makes sure the same feature branch exists in each sibling repo before the flow edits it.
- `/sdd:review` commits and opens a **linked PR in every one** of them.
- `init` adds the sibling repos to `permissions.additionalDirectories`.

<Aside type="note">
A Claude Code session loader (`CLAUDE.md`, root or per-module) stays yours: the framework never reads, writes or enforces it.
</Aside>
