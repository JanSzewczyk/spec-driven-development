Commands invoke agents through the Agent tool; you never call them directly. Implementation is whatever flow you configure.

| Agent | Model | Role |
|---|---|---|
| [`spec-verifier`](#spec-verifier) | <Badge text="Sonnet" variant="note" /> | Reads the diff against the docs. Never writes code or judges quality. |
| [`reviewer`](#reviewer) | <Badge text="Opus" variant="danger" /> | Final audit. Decides READY or NOT READY. |
| [`codebase-surveyor`](#codebase-surveyor) | <Badge text="Haiku" variant="success" /> | Maps the code before the plan. At most 30 lines. |

## spec-verifier

One read of the feature diff against the documentation: every acceptance criterion (met or unmet, with evidence), non-goal violations, out-of-scope changes, drift between `spec.md`, `plan.md`, `tasks.md` and code, and the completeness of each task.

**Called by** [`/sdd:review`](/spec-driven-development/2.0/commands/review/) and [`/sdd:analyze`](/spec-driven-development/2.0/commands/analyze/). **Output:** JSON.

```json
{
  "satisfied": true,
  "ac": [{"id": "AC1", "status": "met", "evidence": "src/auth/reset.py:42"}],
  "non_goal_violations": [],
  "out_of_scope": [{"file": "src/Header.tsx", "summary": "unrelated logo change"}],
  "drift": [{"layer": "plan→tasks", "detail": "plan.md L67 names packages/sms/twilio.ts, no task creates it"}],
  "tasks": [{"id": "T1", "status": "complete", "unmet_ac": []}]
}
```

<Aside type="caution" title="Strict limits">
  It **never** writes code, **never** suggests fixes and **never** judges code quality. That is `reviewer`'s job.
</Aside>

## reviewer

Final quality audit before the PR.

**Called by** `/sdd:review`, which passes the test results and the `spec-verifier` and extra-check results. It does not re-run the suite or start sub-agents itself.

1. Reads the test results (any failure means NOT READY).
2. Checks coverage against the targets in constitution §6.
3. Checks the diff against every **WHAT NOT TO DO** rule, one line per rule.
4. Runs the audit skills configured for each touched project, or with `auto` picks the ones the session has for its stack.
5. Writes `specs/<slug>/review.md` with the verdict.

It **never** returns READY if a test fails, `spec-verifier` is not satisfied, an extra check failed, or a critical security or accessibility violation exists.

**Output:** JSON `{verdict: "READY" | "NOT_READY", blockers: [...], warnings: [...]}`.

## codebase-surveyor

Read-only map of the projects a feature touches, so [`/sdd:plan`](/spec-driven-development/2.0/commands/plan/) reuses what exists.

| Section | Content |
|---|---|
| `Structure` | How each project is laid out. |
| `Conventions` | Naming and test conventions. |
| `Reuse` | `path`: what it does. |

At most 30 lines per run. It says "none found" instead of guessing. It does not search the reference sources linked in the spec; `/sdd:plan` reads those once in its own sub-agent.

<Aside type="tip" title="Your own checks">
  Visual or functional checks of the running app (a QA or UI agent) are yours: add them to `review.checks`.
</Aside>
